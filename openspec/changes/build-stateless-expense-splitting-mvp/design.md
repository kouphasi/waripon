## 背景

現在のリポジトリには、プレーンテキストを返すだけの最小限のTypeScript製Hono Workerがあります。アプリケーションを対話型にする一方で、ユーザーが入力したすべての状態はブラウザまたは共有URL内に保持し、認証済みバックエンド、データベース、サーバー側セッションは使用しません。目的については `proposal.md`、外部から確認できる振る舞いについては3つのdelta specを参照してください。

主な技術的制約は、整数円の合計を正確に維持すること、決定的に精算すること、CSVを安全に取り込むこと、およびURLの実用的な長さとプライバシーの限界です。

## 目標と対象外

**目標:**

- 計算元となる状態を、負担割り当て、差額、送金といったすべての導出結果から分離します。
- 計算関数を決定的かつ副作用のないものにし、個別にテストできるようにします。
- グループ全体で1回の端数調整を適用するまで、均等負担の小数部分を正確に維持します。
- 手入力、CSVインポート、URL復元に対して、共通の検証済み状態境界を使用します。
- 既存のCloudflareデプロイを通して、アプリケーションをブラウザ向けアセットとして配信します。

**対象外:**

- 精算時の送金件数が理論上最小であることの保証。
- 共有状態の暗号化または真正性の保証。
- 共有URLを生成する前の下書きを、現在のブラウザページ外へ永続保存すること。
- バージョン1より前の旧状態形式への対応。

## 設計判断

### ブラウザ中心のTypeScriptアプリケーションを構築する

対話型UIにはViteでビルドするブラウザアプリケーションを使用し、既存のWorkerデプロイから本番アセットを配信するようWranglerを設定します。Honoはアプリケーションシェルやアセットのフォールバックルートが役立つ場合にのみ残し、データAPIは追加しません。

これにより、ブラウザコードをWorkerコードから分離し、フォーム、CSVファイルへのアクセス、フラグメントのデコード、Clipboard APIを通常のブラウザビルドで扱えます。Honoから大きなインラインスクリプトを返す方法は、モジュール単位のテストと保守を難しくするため採用しません。サーバーレンダリングによるフォーム処理は、URLフラグメントを意図的にサーバーから参照できず、編集のたびに不要なリクエストも発生するため採用しません。

### 正規化された計算元の状態だけを保持する

次と同等のバージョン付き正規モデルを使用します。

```ts
type CalculationStateV1 = {
  version: 1
  currency: 'JPY'
  participants: Array<{ id: string; name: string }>
  expenses: Array<{
    id: string
    description: string
    amount: number
    payerId: string
    burdenParticipantIds: string[]
  }>
  roundingAssigneeId: string | null
}
```

ブラウザ内で外部から意味を推測できない安定したIDを生成します。円金額は、検証済みの正の安全な整数として保持します。計算済みの負担額、差額、送金はシリアライズしません。古い結果や改ざんされた結果がUIへ入り込まないよう、状態遷移のたび、およびURLからの復元後に導出します。

状態を入力するすべての経路から共通のスキーマ検証を呼び出します。相互参照の検証では、前後の空白を除去した名前の一意性、IDの一意性、有効な支払者IDと負担者ID、空でない負担者一覧、および参加者が存在する場合の有効な端数調整担当者を確認します。

### 正確な有理数演算で負担額を割り当てる

各支払いについて、選択されたそれぞれの参加者の正確な集計負担額へ `amount / burdenParticipantCount` を加算します。途中の有理数の分子と分母は浮動小数点数ではなく `bigint` で表し、集計時に約分します。

集計後は次のように処理します。

1. 端数調整担当者以外の正確な集計負担額を整数円へ切り捨てます。
2. 担当者へ「支払い総額 - 担当者以外の負担額合計」を割り当てます。
3. 表示する整数円の端数調整額を「担当者へ割り当てた負担額 - 担当者の正確な集計負担額を切り捨てた値」と定義します。

この方法では、ユーザーが選んだ端数調整の役割をグループ全体へ一度だけ適用し、支払いごとの偏りの繰り返しと浮動小数点の誤差を避けながら、常に合計を維持できます。支払いごとに個別に丸める方法は、同じ参加者が繰り返し有利になる可能性があり、グループ単位のradio選択の意味も薄れるため採用しません。

### 決定的な貪欲法で送金を生成する

`balance = paid - assigned burden` として差額を計算します。参加者の安定した順序で支払側と受取側を走査し、現在の支払額と受取額のうち小さい方を送金額として、差額が0になった側を次へ進めます。この方法では、正の整数円の送金だけを生成し、すべての差額を精算できます。また、連結した結果について送金数は最大でも「参加者数 - 1」件になります。

送金件数を厳密に最小化する方法はMVPでは採用しません。貪欲法の出力は予測しやすく検証も簡単ですが、厳密な最小化は各人が最終的に支払う金額を変えない一方で、組み合わせの複雑さを増すためです。

### 明示的な編集状態と導出結果の表示を使用する

UI層では正規化された状態を1つだけ保持し、参加者の作成・更新・削除、支払いの作成・更新・削除、担当者選択、確認済みCSVによる置き換え、URL復元のための状態遷移を提供します。各遷移の後に、副作用のない関数を通して再計算します。状態が不完全な場合は、不完全な精算結果を作るのではなく、結果欄を無効化するか理由を注記します。

支払いから参照されている参加者の削除は拒否します。参照されていない端数調整担当者を削除した場合は、残っている先頭の参加者を選択します。新しく作成する支払いでは、現在の全参加者を初期の負担者として選択します。

### 標準仕様に対応した解析器でCSVを解析し、一括で置き換える

行やカンマを手動で分割するのではなく、UTF-8のBOMとRFC形式の引用符を扱える、保守されているCSV解析器を使用します。CSVフィールドをデコードした後、`split_among` をパイプ区切りの一覧として解析します。置き換え候補の状態を構築し、行番号付きの検証エラーを収集します。候補全体が検証に合格し、ユーザーがプレビューを確定するまでは何も反映しません。

確定したインポートでは、参加者と支払いを置き換え、新しい安定IDを生成し、先頭の参加者を担当者として選択します。曖昧なマージ動作と参加者名の重複を避けるため、置き換え方式を採用します。画面には、仕様の列に一致するダウンロード可能または表示可能なテンプレートを用意します。

### バージョン付き状態をURLフラグメントへ格納する

正規化された状態を簡潔なJSONとしてシリアライズし、そのUTF-8バイト列をブラウザ対応のdeflateストリームで圧縮してbase64urlへ変換し、`#state=<payload>` のような名前空間付きフラグメントキーへ格納します。JSONにバージョンを含め、エンコード前後の防御的なサイズ制限を適用します。MVPでは8,000文字を共有URLの上限とし、それを超える場合は計算内容を減らすよう案内します。

フラグメントはHTTPリクエストや通常のサーバーアクセスログへ送信されないため、クエリパラメーターより適しています。JWTの署名では名前や支払いを隠せず、URLが長くなり、ユーザー自身が作る状態を保護する意味のある鍵管理も必要になるため採用しません。クライアントの同じバンドルへ鍵を含めても有効な秘匿性を提供できないため、暗号化も採用しません。

復元時は、デコード結果を未検証の値として扱い、サイズ制限を適用して、バージョンと完全なスキーマを検証した後に結果を導出します。無効な入力によって現在の状態を部分的に変更しません。共有画面では、URLを知る人なら誰でも内容を読めること、およびブラウザ履歴やメッセージングシステムにリンクが残る可能性を明示します。

### ドメイン境界ごとに独立してテストする

有理数集計、調整額の割り当て、差額合計の維持、送金による精算を単体テストし、代表的な生成入力に対するプロパティ形式の不変条件も確認します。CSVについては、引用符、BOM、空白、一括失敗、プレビュー変換を重点的にテストします。URLについては、往復変換、不正データ、過大データ、バージョンをテストします。主要な手入力、担当者選択、CSV確定、共有リンクの各フローをブラウザレベルでテストします。

## リスクとトレードオフ

- [大きな支払い明細が実用的なURL長を超える] → 状態を圧縮して導出結果を除外し、8,000文字の上限を適用して、計算内容を減らすよう案内します。ファイルへのエクスポートは将来追加できます。
- [共有リンクから個人的な支払い情報が見える] → データをフラグメントに保持し、受取人が読めることを明示して、暗号化や機密性があるとは説明しません。
- [選択した担当者が、自分の参加していない支払いから生じた端数も引き受ける] → グループ全体の調整担当であることを明確に表示し、整数円の調整額を示して、共有前に担当者を切り替えられるようにします。
- [貪欲法による精算は送金件数が常に最小とは限らない] → 「最小の精算」ではなく「決定的な精算」と説明し、計算の正しさに関する不変条件を維持します。
- [古いブラウザでは圧縮APIの対応状況が異なる] → リンク生成前に必要なブラウザ機能を検出し、壊れたリンクを生成せず、未対応ブラウザであることを明確に表示します。
- [将来CSVエクスポートを追加すると、CSV数式が危険になる可能性がある] → MVPではCSVを単なるテキストとして読み取ります。将来エクスポートする場合は、表計算ソフトの数式をエスケープする仕様を別途定めます。

## 移行計画

1. デプロイ済みルートを変更せず、ブラウザビルドとテストを追加します。
2. 正規化された状態の検証と、副作用のない計算モジュールを実装して検証します。
3. UI、CSVインポート、URLフラグメントの変換処理を接続します。
4. ビルド済みアセットを配信するようWranglerを設定し、新しいアプリケーションをデプロイします。
5. 有効な共有リンク、不正なリンク、代表的なCSVを使ってスモークテストします。

ロールバックする場合は、以前のWorkerバンドルを再デプロイします。保存済みのユーザーデータや、元に戻す必要のあるスキーマ移行はありません。
